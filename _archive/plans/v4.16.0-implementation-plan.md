## 0. Executive Summary

One major work item ships in v4.16.0:

| Item | Title | Size | Stories | Estimated Points |
|------|-------|------|---------|-----------------|
| 4X-6 | Consolidated Power Panel (Area Grouping) | L | 7 | 26 |

**Nature of change**: Enhancement to existing 4X-3 power panel infrastructure. This is NOT a rewrite — it reorganizes how power devices are rendered per area. Most sub-renderers (`_renderCircuitTile`, `_renderPowerDeviceRow`, `_renderPowerStrip`, `_renderStripChild`, `_renderPowerSummaryCard`, `_renderPowerArc`) already exist and ship in v4.15.x.

**Core change**: Currently each power device gets its own panel in the right column. After this enhancement, ALL power devices in an area are aggregated into ONE consolidated panel rendered at the bottom of the left content column — ~80% vertical space reduction in power-heavy areas.

**Bundle impact**: Minimal. New code is ~120 lines of JS (aggregation logic + consolidated renderer that delegates to existing sub-renderers) + ~150 lines of CSS (consolidated panel frame + section styling + Geordi amendments). Estimated delta: ~4–6 KB uncompressed (<2% increase from 343 KB baseline).

**Risk level**: LOW. All existing sub-renderers are reused. The main risk is the `_renderAreaContent()` routing change — a well-understood code path with clear before/after behavior.

## 4. Implementation Sequence

### Story 1: Intercept Power Devices in `_renderAreaContent()` — 3 pts (S)

**As a** homepage card, **I need** power devices to be collected separately from other panel devices during area rendering, **so that** they can be aggregated into a single consolidated panel instead of N individual panels.

**File modified**: `src/lcars-homepage-card.js`

**Implementation**:

**Change 1** — `_renderAreaContent()` (line ~6759): Add `powerGroups` array and divert `PANEL_TYPE_POWER` groups away from `panelDevices`:

```js
// BEFORE:
const panelDevices = [];
const normalDevices = [];
for (const group of byDevice.values()) {
  const panelType = this._getDevicePanelType(group.entities);
  if (panelType) {
    panelDevices.push({ ...group, panelType });
  } else {
    normalDevices.push(group);
  }
}

// AFTER:
const panelDevices = [];
const normalDevices = [];
const powerGroups = [];
for (const group of byDevice.values()) {
  const panelType = this._getDevicePanelType(group.entities);
  if (panelType === PANEL_TYPE_POWER) {
    powerGroups.push({ ...group, panelType });
  } else if (panelType) {
    panelDevices.push({ ...group, panelType });
  } else {
    normalDevices.push(group);
  }
}
```

**Change 2** — Same method, `normalContent` template: Append consolidated power panel placeholder at bottom of normal content stack:

```js
// After the noDevice block in normalContent:
${powerGroups.length > 0 ? this._renderConsolidatedPowerPanel(
  this._buildPowerCollection(powerGroups)
) : ''}
```

**Change 3** — `_renderDevicePanel()` (line ~4020): Remove `case PANEL_TYPE_POWER:` from the switch statement. Power devices no longer route through the right-column panel dispatch.

**Temporary**: Until Story 4 creates `_renderConsolidatedPowerPanel()`, this story adds a stub that returns a placeholder `html`\`<div class="lcars-consolidated-power-panel">POWER PANEL PLACEHOLDER</div>\`\` so the routing can be verified.

**Acceptance criteria**:
- [ ] Power devices no longer appear in `area-split-panels` (right column)
- [ ] Power devices are intercepted into `powerGroups[]` array
- [ ] Non-power panel devices (camera, climate, battery, etc.) still render in right column unchanged
- [ ] Normal devices still render in left column unchanged
- [ ] Areas with zero power devices render identically to before
- [ ] Areas with ONLY power devices fall back to single-column layout (no empty right column)

**Definition of Done**: Routing verified visually — power devices removed from right column, placeholder visible in left column.

**Review gate**: Data (architecture — routing change correctness)

### Story 2: `_buildPowerCollection()` Aggregation Method — 5 pts (M)

**As a** consolidated power panel, **I need** all power device groups for an area classified by type (vue/plug/strip) and aggregated into a structured collection, **so that** the renderer can display circuits, plugs, and strips in organized sections.

**Depends on**: Story 1 (powerGroups array)

**File modified**: `src/lcars-homepage-card.js`

**Implementation**: New method `_buildPowerCollection(powerGroups)` per spec §1.3.

**Logic flow**:
1. Classify each group via existing `_classifyPowerDevice()` → `'vue'`/`'plug'`/`'strip'`
2. Separate into `vueCircuits[]`, `plugs[]`, `stripParents[]`
3. Use existing `_groupPowerStrips()` to assign plug children to strip parents via `via_device_id`
4. Process circuits through existing `_detect240VPairs()` → `_sortCircuits()` pipeline
5. Compute area-wide `totalWatts` and `totalEnergy` from all groups
6. Return structured `{ circuits, plugs, strips, totalWatts, totalEnergy, deviceCount }`

**Key design decisions**:
- Reuses `_groupPowerStrips()` (line ~6310) which already implements the `via_device_id` parent→child grouping — **do not duplicate** this logic
- Plugs not matched to any strip parent become "orphan plugs" in the MONITORED DEVICES section
- Vue circuits and unclassified sensor-only devices both render as circuit tiles

**Acceptance criteria**:
- [ ] Area with 6 Vue circuits → `collection.circuits` has 6 entries (after 240V pairing, may be fewer)
- [ ] Area with 2 strips (6 outlets each) → `collection.strips` has 2 entries, each with `children[]` populated
- [ ] Area with 1 orphan plug → `collection.plugs` has 1 entry
- [ ] `totalWatts` sums all primary power across all device types
- [ ] `totalEnergy` sums all primary energy across all device types
- [ ] `deviceCount` reflects total input groups
- [ ] Empty area (0 power groups) → method is not called (guarded by `powerGroups.length > 0` check in Story 1)

**Definition of Done**: Collection object tested with multi-device area (Server Room: 6 circuits + 2 strips). Console-log confirms correct classification and totals.

**Review gate**: Data (architecture — collection structure, no duplicate logic)

### Story 3: `_renderClickableValue()` + Enhanced Sub-Renderers — 5 pts (M)

**As a** user, **I want** every power metric (watts, energy) to be clickable and open the HA more-info dialog, **so that** I can inspect history and details for any individual sensor.

**Depends on**: Story 2 (collection structure defines entity relationships)

**File modified**: `src/lcars-homepage-card.js`

**Implementation**:

**New method** — `_renderClickableValue(entityId, ariaLabel, displayHtml)`:
```js
_renderClickableValue(entityId, ariaLabel, displayHtml) {
  if (!entityId) return displayHtml;
  return html`
    <span class="power-clickable-value"
      role="button" tabindex="0"
      aria-label="${ariaLabel}"
      @click=${(e) => { e.stopPropagation(); this._handleEntityClick(entityId); }}
      @keydown=${(e) => { if (e.key === 'Enter' || e.key === ' ') { e.preventDefault(); this._handleEntityClick(entityId); } }}>
      ${displayHtml}
    </span>
  `;
}
```

Note: `ariaLabel` parameter satisfies Geordi amendment G-4 (specific labels, not generic "View details"). Labels follow the pattern: `"View [device name] [metric]: [value]"`.

**Enhanced method 1** — `_renderCircuitTile(circuit)`:
- Find `powerEntityId` and `energyEntityId` from `circuit.entities`
- Wrap watts display in `_renderClickableValue(powerEntityId, 'View ${name} power: ${watts}W', html`...`)`
- Wrap energy display in `_renderClickableValue(energyEntityId, 'View ${name} energy: ${energy} kWh', html`...`)`
- Tile-level click still opens popover (existing behavior unchanged)

**Enhanced method 2** — `_renderStripChild(childGroup)`:
- Find `powerEntityId` and `energyEntityId` from `childGroup.entities`
- Wrap watts in `_renderClickableValue()` with specific label
- Add energy display (currently absent from strip children) wrapped in `_renderClickableValue()`

**Enhanced method 3** — `_renderPowerDeviceRow(group)`:
- Find `powerEntityId` and `energyEntityId`
- Wrap watts/energy values in `_renderClickableValue()` with specific labels

**Acceptance criteria**:
- [ ] Clicking a circuit tile's watts value opens more-info for the power sensor entity
- [ ] Clicking a circuit tile's energy value opens more-info for the energy sensor entity
- [ ] Clicking a strip child's watts value opens more-info for that outlet's power sensor
- [ ] Clicking a plug row's watts value opens more-info for that plug's power sensor
- [ ] Each clickable value has a unique, descriptive `aria-label` (G-4)
- [ ] Keyboard: Enter/Space on a clickable value triggers more-info
- [ ] Click events do not propagate to parent tile/row handlers (e.stopPropagation)
- [ ] Entities without a backing sensor ID render the value without click wrapper (graceful degradation)

**Definition of Done**: All clickable values verified in dev HA environment. Screen reader announces specific labels.

### Story 6: Truncation Pattern for Large Sections — 3 pts (S)

**As a** user with many power devices (e.g., 40+ Vue circuits), **I want** sections with 12+ items to show a truncated view with a "SHOW ALL" expansion pill, **so that** the panel remains compact by default but I can see everything when needed.

**Depends on**: Story 4 (sections exist), Story 5 (CSS ready)

**File modified**: `src/lcars-homepage-card.js`

**Implementation**:

**JS logic**: In `_renderConsolidatedPowerPanel()`, wrap each section's item list in a truncation pattern:

```js
// For each section (circuits, plugs, strips):
const MAX_VISIBLE = 12;
const isExpanded = this._expandedPowerSections?.has(sectionKey) || false;
const visibleItems = isExpanded ? items : items.slice(0, MAX_VISIBLE);
const hasMore = items.length > MAX_VISIBLE;
```

**Expansion state**: Track expanded sections in a `Set` on the component instance:
- `this._expandedPowerSections = this._expandedPowerSections || new Set()`
- Toggle handler: add/remove section key from Set, trigger `requestUpdate()`

**Pill button**: After the truncated list, render:
```html
${hasMore && !isExpanded ? html`
  <button class="power-show-all-pill"
    aria-label="Show all ${items.length} ${sectionLabel}"
    @click=${() => { this._expandedPowerSections.add(sectionKey); this.requestUpdate(); }}>
    SHOW ALL (${items.length})
  </button>
` : ''}
```

**CSS for pill**:
- LCARS-styled pill button: `var(--lcars-gray)` background, uppercase, rounded, hover glow
- Positioned at bottom of section, centered

**Acceptance criteria**:
- [ ] Section with ≤12 items renders all items, no pill visible
- [ ] Section with 13+ items renders first 12 + "SHOW ALL (N)" pill
- [ ] Clicking pill expands to show all items
- [ ] Pill disappears after expansion
- [ ] Expansion state persists during same area view (doesn't reset on every render)
- [ ] Each section expands independently
- [ ] Pill is keyboard accessible (focusable, Enter/Space activates)

**Definition of Done**: Tested with Main Panel (40+ circuits) — truncation and expansion work correctly.

**Review gate**: Geordi (accessibility — pill button meets WCAG), Data (performance — confirms no unnecessary re-renders from expansion state)

## 6. Risk Register

| Risk | Probability | Impact | Mitigation |
|------|------------|--------|------------|
| `_renderAreaContent()` routing change causes regression in non-power areas | Low | High | Story 1 includes explicit verification that non-power panels render unchanged. Story 7 includes cross-area regression check. |
| Strip child assignment fails for non-TP-Link brands | Low | Medium | `_groupPowerStrips()` uses HA's standard `via_device_id` field — brand-agnostic. Orphan plugs fall back safely to MONITORED DEVICES. |
| Truncation expansion state resets on HA re-render | Medium | Low | State stored on component instance (`this._expandedPowerSections`). If HA forces a full re-render, expansion resets — acceptable UX. |
| Large circuit count (40+) causes jank on initial render | Low | Medium | Truncation pattern (Story 6) limits initial DOM to 12 tiles. Scroll + fade mask for overflow. No change to sparkline lazy-loading. |
| CSS specificity conflicts with existing power panel styles | Low | Medium | Consolidated panel uses `.lcars-consolidated-power-panel` namespace — all new selectors are scoped to this class. No collision with `.lcars-device-panel.power-panel`. |
